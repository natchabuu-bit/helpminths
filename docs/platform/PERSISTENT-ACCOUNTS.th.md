# เก็บบัญชี HelpMinths ให้คงอยู่บน Render

บัญชีที่สมัครและอนุมัติแล้วต้องอยู่ในฐานข้อมูลถาวร ไม่ขึ้นกับการเปิดเว็บในแต่ละวัน การหมดอายุการเข้าสู่ระบบเพียงทำให้ต้องเข้าสู่ระบบอีกครั้งด้วยบัญชีเดิม ไม่ควรทำให้ต้องสมัครและรออนุมัติใหม่

## สาเหตุของการต้องสมัครใหม่

การตั้งค่าเดิมใน `render.yaml` ใช้ Render Free และเปิด `HELPMINTHS_AUTO_STORAGE=1` บริการจึงเก็บ SQLite กับภาพไว้ใน `/var/lib/helpminths` ของเครื่องบริการชั่วคราว เมื่อโฮสต์เปลี่ยนหรือสร้างเครื่องใหม่ ข้อมูลบนพื้นที่นี้อาจหาย ทั้งบัญชี การอนุมัติ ประวัติ และภาพ การเพิ่มอายุ cookie หรือ session ไม่ทำให้ฐานข้อมูลนี้ถาวร

แนวทางที่เข้ากับระบบปัจจุบันคือผูก Persistent Disk จริงเข้ากับบริการเดิม ให้ SQLite และภาพอยู่บน disk นั้น แล้วสำรองข้อมูลแยกอีกชุด

## ไฟล์ที่เตรียมไว้

[`render.persistent.yaml`](../../render.persistent.yaml) เป็น **เทมเพลตทางเลือกที่มีค่าใช้จ่าย** ประกอบด้วย:

- บริการ Docker ชื่อ `helpminths` และค่าด้านแดชบอร์ดเดิม
- ตัวอย่าง instance `starter` ซึ่งเป็นจุดเริ่มต้นของแผนแบบเสียเงิน ไม่ใช่คำยืนยันว่า RAM พอสำหรับโมเดล YOLO
- Disk ชื่อ `helpminths-data` ขนาดตัวอย่าง 1 GB ที่ `/var/lib/helpminths`
- พาธเก็บข้อมูลที่ระบุชัดเจน พร้อมปิดโหมดเลือกพื้นที่ชั่วคราวอัตโนมัติ
- `autoDeploy: false` ตามเดิม

ไฟล์ `render.yaml` เดิมยังเป็นแผน Free ไม่มีการซื้อ disk เปลี่ยนแผน หรือ deploy จากการเพิ่มเทมเพลตนี้ เจ้าของบริการต้องตรวจราคา instance และ disk ที่ Render แสดงและอนุมัติก่อนใช้ ขนาด disk ต้องพอกับฐานข้อมูลและภาพที่จะเก็บ ไม่ใช่เพียงจำนวนบัญชี

## สำรองก่อนเปลี่ยนบริการ

**ทำขั้นนี้ก่อนเปลี่ยนแผน เพิ่ม disk restart หรือ deploy** ถ้ายังมีบัญชีและข้อมูลที่ต้องการเก็บอยู่ในบริการปัจจุบัน

1. หยุดการเขียนข้อมูลตามวิธีที่ผู้ดูแลโฮสต์รองรับ แล้วสำรองโฟลเดอร์ข้อมูลส่วนตัวทั้งชุดให้สอดคล้องกัน: SQLite พร้อมภาพและไฟล์ประกอบ
2. หากสำรอง SQLite ขณะออนไลน์ ให้ใช้ SQLite backup API และมีวิธีควบคุมให้ภาพกับรายการฐานข้อมูลตรงกัน การคัดลอกเฉพาะ `.sqlite3` ขณะที่มีผู้เขียนข้อมูลอาจไม่ครบ รวมถึงกรณีที่ยังมี WAL
3. เก็บชุดสำรองไว้นอก disk ต้นทางในพื้นที่ส่วนตัว และทดสอบว่าเปิดฐานข้อมูล/ภาพได้ ห้ามนำฐานข้อมูลบัญชี password hashes หรือภาพส่วนตัวใส่ GitHub สาธารณะ

แผน Free อาจไม่มี Shell/SSH ให้ดึงไฟล์ จึงต้องตรวจช่องทางสำรองที่บริการปัจจุบันรองรับก่อน การอัปเกรดแผนเพื่อหวังเปิด Shell ภายหลังอาจสร้างเครื่องใหม่และสูญเสียไฟล์ชั่วคราวไปก่อนแล้ว หากยังสำรองข้อมูลที่เหลือไม่ได้ ต้องให้เจ้าของโฮสต์จัดการขั้นย้ายข้อมูลนี้ก่อน ไม่ควรถือว่าการเปลี่ยนแผนจะย้ายบัญชีให้เอง

การ mount disk ใหม่ทับ `/var/lib/helpminths` **ไม่ได้คัดลอกข้อมูลเดิมมาให้** และอาจบังข้อมูลเดิมที่อยู่ตรงพาธนั้น Disk ใหม่เริ่มว่าง ต้อง restore ชุดสำรองลง disk ขณะที่ไม่มีผู้เขียนข้อมูล

ดูวิธีสำรองและ restore เพิ่มเติมที่ [คู่มือแพลตฟอร์ม](README.th.md#สำรองข้อมูลและการเก็บรักษา) ชุดสำรองโค้ด Git/ZIP ไม่รวมฐานข้อมูลและภาพส่วนตัวของบริการ บัญชีที่สูญหายไปแล้วกู้กลับจากโค้ดเพียงอย่างเดียวไม่ได้

## ตั้งค่าบริการเดิมใน Render

สำหรับเว็บ `helpminths` ที่มีอยู่แล้ว ให้ทำบน **บริการเดิม** ใน Render Dashboard ไม่สร้างบริการชื่อซ้ำโดยไม่ตั้งใจจาก Blueprint อีกชุด

หลังสำรองข้อมูลปัจจุบันเรียบร้อย:

1. เปิด Render Dashboard → เลือกบริการ `helpminths`
2. ในส่วน instance/compute เลือกแผนแบบเสียเงินที่รองรับ Persistent Disk และมี RAM พอกับโมเดลจริง ตรวจยอดค่าใช้จ่ายก่อนยืนยัน แผนตัวอย่าง `starter` อาจต้องเพิ่มขนาดเพื่อใช้ YOLO
3. เพิ่ม Persistent Disk ตามเมนูที่ Render แสดง ตั้ง mount path เป็น `/var/lib/helpminths` และเลือกความจุตามปริมาณภาพ/ระยะเก็บที่ต้องการ
4. ใน Environment ตั้งค่าดังตาราง โดยคงค่าลับของเจ้าของ โมเดล และแดชบอร์ดที่ใช้อยู่เดิม:

| ตัวแปร | ค่า |
|---|---|
| `HELPMINTHS_DATA_DIR` | `/var/lib/helpminths` |
| `HELPMINTHS_AUTO_STORAGE` | `0` |
| `HELPMINTHS_STORAGE_DURABLE` | `1` |

5. Restore ฐานข้อมูลและภาพจากชุดสำรองลง disk จริง โดยหยุดการเขียนข้อมูลระหว่าง restore คงสิทธิ์ไฟล์ส่วนตัวและ schema ที่ระบบรองรับ
6. บันทึกการตั้งค่าและ deploy รุ่นโค้ดที่ต้องการตามขั้นตอนของ Render ใช้ HTTPS และ Secure cookie ตามค่า production เดิม

`HELPMINTHS_STORAGE_DURABLE=1` เป็นเพียงคำประกาศของผู้ดูแล **ไม่ใช่คำสั่งสร้าง disk** การระบุพาธโดยไม่ได้ผูก disk จริงยังทำให้ข้อมูลสูญหายได้ เช่นเดียวกับการอัปเกรด instance โดยไม่เพิ่ม disk

สำหรับการจัดการด้วย Blueprint ให้เจ้าของตรวจ `render.persistent.yaml` ทั้งไฟล์และขั้นตอนผูกกับบริการเดิมก่อนนำไปใช้ ห้ามวางฐานข้อมูลจริงไว้ใน Docker image หรือหวังให้ขั้น build เขียนข้อมูลลง disk runtime

## ตรวจรับหลังย้าย

- ตรวจใน Render ว่า disk ผูกกับบริการเดิมและ mount path ตรงกับ `HELPMINTHS_DATA_DIR`
- ตรวจชื่อบัญชีเดิม รหัสบัญชี บทบาท และสถานะอนุมัติหลัง restore พร้อมตรวจภาพและประวัติที่เกี่ยวข้อง
- ใช้บัญชีทดสอบสมัคร/อนุมัติหนึ่งครั้ง แล้วตรวจว่าเข้าสู่ระบบด้วยบัญชีเดิมได้หลัง restart บริการ และหลัง deploy ใหม่ โดยไม่ต้องสมัครซ้ำ
- ตรวจฐานข้อมูลและภาพเก่าพร้อมกัน การเห็นหน้าเว็บหรือสถานะ `durable` อย่างเดียวไม่พิสูจน์ว่าดิสก์เก็บข้อมูลจริง
- สำรองข้อมูลไว้นอก disk เป็นรอบและทดสอบ restore ตามนโยบายหน่วยงาน

เมื่อต่อ disk ถูกต้อง บัญชีจะไม่ถูกล้างเพียงเพราะโฮสต์เริ่มใหม่หรือ deploy ผู้ใช้ยังอาจต้องเข้าสู่ระบบอีกครั้งเมื่อ session หมดอายุ ซึ่งใช้ชื่อบัญชีและรหัสผ่านเดิมได้ กฎยืนยันตัวตนผู้เชี่ยวชาญและสิทธิ์เข้าถึงภาพไม่เปลี่ยนจากขั้นตอนจัดเก็บนี้

Persistent Disk ไม่รับประกันการคงอยู่หากถูกลบ บริการถูกยกเลิก หรือไม่มีพื้นที่เหลือ จึงต้องมีการสำรองและนโยบายเก็บรักษา ระบบ SQLite กับ disk ส่วนตัวนี้ใช้กับบริการเครื่องเดียว หากเพิ่มหลาย replica ต้องออกแบบฐานข้อมูลและที่เก็บภาพร่วมกันก่อน

เอกสารนี้เตรียมวิธีตั้งค่าและเทมเพลตไว้ ยังไม่ได้ยืนยันว่าบริการออนไลน์ได้รับ disk หรือ deploy การเปลี่ยนแปลงแล้ว
